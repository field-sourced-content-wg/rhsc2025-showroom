:source-highlighter: rouge

モジュール 1 では、開発環境と Red Hat Developer Lightspeed for MTA (以下、Developer Lightspeed) プラグインの接続を確立しました。いよいよ本番です。

Legacy Java Japan カンパニーの上司から連絡が入りました。「パイロットの準備はできた。coolstore を使って、Java EE から Quarkus への移行を実際にやってみてほしい。AI がどこまで使えるか確認したい。」

このモジュールでは、Java EE サンプルアプリケーション link:https://github.com/field-sourced-content-wg/coolstore/tree/rhsc2025-handson[coolstore^] に対してソースコードの静的解析を実行します。Developer Lightspeed が提案する変更を確認し、コードを Quarkus 向けに書き換えます。最後にリポジトリ同梱のスクリプトでビルド・OpenShift デプロイし、動作を確認します。

== 学習目標

このモジュールを完了すると、以下のことができるようになります:

* Developer Lightspeed プラグインからソースコードの静的解析を実行し、解析レポートを読み解く
* AI が提案する移行パッチを確認し、EJB から CDI への変換など主要な変更を適用する
* 移行後の Quarkus アプリケーションをビルドし、OpenShift にデプロイして動作確認する

== 背景: Java EE から Quarkus への移行で何が変わるか

coolstore は Java EE 7 のモノリシックアプリケーションです。EJB、JMS、JSF を含む典型的な構成を持ち、Quarkus への移行では次の変更が必要になります。

* **EJB から CDI へ**: `@Stateless`、`@Stateful` などの EJB アノテーションは、CDI の `@ApplicationScoped`、`@RequestScoped` に置き換わります
* **JAX-RS の調整**: エンドポイントの構成は基本的に互換性がありますが、Quarkus 固有の設定が必要な箇所があります
* **pom.xml の依存関係**: Java EE の依存関係を Quarkus BOM と各種 Quarkus エクステンションに置き換えます
* **設定ファイル**: `persistence.xml` などの設定は `application.properties` に統合されます

ソースコードの静的解析でこれらの変更箇所を自動的に検出し、Developer Lightspeed がコード変更の提案を生成します。

== エクササイズ 1: ソースコードの静的解析の実行

まず coolstore に対してソースコードの静的解析を実行し、Quarkus 移行に必要な作業を洗い出します。解析結果がこのあとのすべての作業の出発点になります。

== エクササイズ 2: AI 提案によるコード変更の適用

静的解析が完了しました。Developer Lightspeed が提案する変更を確認し、Java EE のコードを Quarkus 向けに書き換えます。EJB から CDI への変換、JAX-RS の調整、pom.xml の依存関係更新が主な作業です。

=== 前提条件

* エクササイズ 1 でソースコードの静的解析が完了していること
* Developer Lightspeed のサイドパネルに Issues が表示されていること

=== 手順

. Developer Lightspeed のサイドパネルで最初の Issue をクリックします。Issue の詳細が表示されます。

. 詳細内容を確認したら「スパナ」アイコンをクリックして Developer Lightspeed に修正内容の提案を依頼します。提案の根拠や修正内容／方針などは Result View に表示されます。

. EJB アノテーションの変換を手動でも確認します。変換前後の典型的なパターンは次の通りです:
+
[source,text]
----
変換前 (Java EE):
import javax.ejb.Stateless;
@Stateless
public class SampleService { ... }

変換後 (Quarkus / CDI):
import javax.enterprise.context.ApplicationScoped;
@ApplicationScoped
public class SampleService { ... }
----

. JAX-RS のエントリポイントを確認します。Quarkus ではアプリケーションクラスが不要な場合があります:
+
[source,bash,role="execute"]
----
find src -name "*.java" -exec grep -l "javax.ws.rs.core.Application\|ApplicationPath" {} \;
----
+
該当ファイルが見つかった場合、Developer Lightspeed の提案を参考に削除または修正します。

. `pom.xml` を Quarkus 用に更新します。Developer Lightspeed の提案を適用した後、依存関係が正しく置き換わっているか確認します:
+
[source,bash,role="execute"]
----
grep -E "quarkus|javax.ejb|javax.persistence" pom.xml | head -20
----

. Quarkus BOM と必要なエクステンションが追加されていない場合、ターミナルから追記します:
+
[source,bash,role="execute"]
----
cd /projects/coolstore
mvn quarkus:add-extension -Dextensions="resteasy-reactive,hibernate-orm-panache,jdbc-postgresql"
----

. データソースと Keycloak の設定は、エクササイズ 3 の `01-setup.sh` が PostgreSQL と `keycloak.json` を用意します。ここではソースコード上の Issues 対応に集中してください。

. 変更したファイルを保存し、Developer Lightspeed のサイドパネルで残りの Issues 数が減っていることを確認します。
+
image::module02-ai-fix-applied.png[Developer Lightspeed が提案した修正を適用した画面,link=self,window=blank,width=700]

=== 確認

主要な変更が正しく適用されていることを確認します。

[source,bash,role="execute"]
----
# EJB アノテーションが残っていないか確認
grep -r "javax.ejb" src/ && echo "EJB 参照が残っています" || echo "EJB 参照はありません"

# Quarkus 依存関係の確認
grep -c "quarkus" pom.xml
----

`EJB 参照はありません` と表示され、`pom.xml` に複数の `quarkus` 参照があれば、コード変換は完了しています。

=== よくある問題

**問題**: `Apply Fix` ボタンをクリックしても変更が反映されない

→ **解決方法**: ファイルが読み取り専用になっていないか確認します:
+
[source,bash,role="execute"]
----
ls -la src/main/java/
----
+
パーミッションに問題がある場合は次を実行します:
+
[source,bash,role="execute"]
----
chmod -R u+w /projects/coolstore/src
----

**問題**: `mvn` コマンドが見つからない

→ **解決方法**: Dev Spaces ワークスペースを再起動するか、ターミナルで `which mvn` を実行して Maven が利用可能か確認してください。

Issue がゼロ件になるまで繰り返してください。（`pom.xml` と `application.properties` を除く）

== エクササイズ 3: 移行後アプリのビルドとデプロイ

コード変更が完了しました。最終ステップです。Quarkus に移行した coolstore をビルドし、OpenShift にデプロイして、実際に動作することを確認します。

=== 前提条件

* エクササイズ 2 でコード変換が完了していること
* OpenShift クラスターへのアクセスが可能であること

=== 手順

. coolstore リポジトリのルート (`/projects/coolstore`) に移動し、Keycloak と PostgreSQL のセットアップを実行します:
+
[source,bash,role="execute"]
----
cd /projects/coolstore
./01-setup.sh
----

. coolstore アプリケーションをビルドします。
+
[source,bash,role="execute"]
----
./02-build.sh
----
+
`BUILD SUCCESS` と表示されることを確認します。ビルドには 2〜5 分かかります。

. coolstore アプリケーションをデプロイします。
+
[source,bash,role="execute"]
----
./03-deploy.sh
----
+
デプロイスクリプト完了時に表示される URL（`https://...`）も確認できます。

=== 確認

. デプロイが完了したら、アプリケーションの URL を取得します（プロジェクト `{user}-wk`、Route 名 `coolstore-quarkus`）:
+
[source,bash,role="execute"]
----
oc get route coolstore-quarkus -n {user}-wk -o jsonpath='{.spec.host}'
----

. 取得した URL をブラウザの別のタブにアクセスして、アプリケーションが正常に応答することを確認します:
+
image::module02-app-deployed.png[OpenShift にデプロイされた Quarkus アプリケーション,link=self,window=blank,width=700]

このモジュールで取り組んだ内容を振り返りましょう。

* **AI 提案の確認と適用**: EJB から CDI へのアノテーション変換、JAX-RS の調整、`pom.xml` の依存関係更新など、主要な変更を AI の提案をもとに適用しました

== モジュールまとめ

Java EE アプリケーションを Quarkus に移行する完全なサイクルを体験しました。静的解析、コード変換、デプロイ。この 3 ステップが AI 支援によってどれだけ短縮できるかを確認できたのではないでしょうか。

**達成したこと:**

* MTA によるソースコードの静的解析で移行箇所を自動検出した
* Developer Lightspeed の提案をもとに、EJB/CDI/JAX-RS/pom.xml の変更を適用した
* Quarkus アプリケーションとして OpenShift にデプロイし、動作確認した

**Legacy Java Japan カンパニーへの価値:**

* **移行速度の向上**: AI による提案で、手動でのコード調査にかかる時間を大幅に短縮できる
* **品質の一貫性**: 同じ静的解析ルールを全アプリに適用することで、移行品質のばらつきを抑えられる
* **リスクの低減**: 静的解析結果に基づいた計画的な移行により、予期しない問題を事前に検出できる

**次のステップ:**

モジュール 3 では、カスタムルールの作成に取り組みます。Legacy Java Japan カンパニー固有の技術スタックや社内ライブラリに対して、MTA が認識できる独自の移行ルールを追加します。標準ルールだけでカバーしきれない移行パターンに対応するスキルを習得します。
